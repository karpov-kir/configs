The two families

The prefix is the contract, not a naming habit.

kk-* — works in any repo

Reviewing, building, diagnosing, refining. Nothing about them assumes a particular way of working.

Drop them into any codebase and they hold. They know the shared writing and engineering standards, and nothing about intents, charters or ships.

idsd-* — one workflow, with state on disk

Intent-driven development: plan a feature, build it, review it, archive it.

They keep a .idsd/ directory — charter, intents, records, reports — and every one of them assumes it exists. If your project has no .idsd/, none of these apply to you.

idsd-*  →  kk-*

The dependency runs one way. A workflow skill calls an any-repo one. The reverse would make a skill that works everywhere carry knowledge of a workflow most repos never use — so when an any-repo skill says what it is not, it names the capability rather than the workflow skill that has it.

The intent-driven path

One reactor coordinates the intent set; separate tasks own each feature.

Use idsd-reactor as the central task for coordinating intents and requesting new ones. Bring new work to that task, including requests that arrive while other features are being built. The reactor starts separate tasks for authoring and shipping; the steps below show the work those tasks own.

0

Seed the project idsd-charter

The what and why of the whole project, plus the limits every feature inherits — the response time you will not exceed, the dependency you will not add. Done once, edited rarely.

writes .idsd/charter.md, including its protected Constraints section

1

Say what to build idsd-intent

One feature becomes an ICE — Intent, Context, Expectations. The goal, what it must respect, and the scenarios that show it works; never how to build it. The skill asks you questions until nothing is left open that could change what gets written, then writes the file.

writes .idsd/intents/NNN-slug/intent.md

Every slice is vertical — storage to interface, demonstrable on its own. "The schema", then "the API", then "the screen" gives you three intents nobody can accept, because none of them changes what a user can do.
2

Ship it idsd-ship

The reactor starts a shipping task for each ready intent. You can also use this skill directly for one feature. It writes the intent first if there isn't one, then runs the three stages below in order and stops to ask you before anything is merged.

idsd-build → idsd-qualify → idsd-finalize

3

Build idsd-build

Settles the questions the intent left open, puts the work on its own branch in its own worktree — a second checkout of the same repository, so two features can be built at once without colliding — then codes and tests until the checks pass. The intent's scenarios are what the tests have to show.

branch idsd/NNN-slug · one worktree per intent

4

Review idsd-qualify

A pipeline of review stages — correctness, security where the change touches any, prose, cleanup — each one a separate pass with its own lens. The result is written down as a report, stamped against the exact version of the code it read.

writes the review report · stamps the version it read

5

Finish idsd-finalize

What the feature taught goes up into the project's own records, then the intent moves to the archive. This runs one at a time across the whole repository, because it writes files every feature shares.

merges decisions · archives the intent

This is the only stage that has to wait its turn. Everything that might ask you a question happens before it — a question asked while the turn is held stalls every other feature behind a thread nobody is watching.

Keep coordination in the reactor

One reactor per intent set. Return to it with new requests.

A request without an intent goes to idsd-reactor. It assigns an intent number and starts a separate idsd-intent task to author the ICE, without building it. Answer that task's questions there. It lands the intent on the target branch and reports back to the reactor.

The reactor tracks the new intent's dependencies and starts an idsd-ship task when it is ready within the approved scope. It coordinates live tasks, relays changes that affect siblings, and starts newly unblocked work as each intent lands. The idsd/audit worker checks consistency and derives the build order.

Keep the reactor task available throughout the run. Bring additions and coordination requests back to it; answer feature-specific questions in the task that asks them.

depends-on → parallel

Dependencies decide what runs together; shared files do not. Two features touching the same code still start at once — the overlap is resolved when each one merges. Hold a pair back only when they would be redoing each other's work.

Three kinds of thing, two places they live

The shape underneath every skill above. Written out here; the standards enforce it.

Everything in this ecosystem is one of three kinds, and the difference is worth knowing because it decides what a request costs you.

  • A session is a skill that does the work itself. It holds the thinking, and it runs at the model tier that work needs. It is a session because something about it needs you — it decides with you, or it holds context only that conversation has, or it does something with no undo.
  • An orchestrator is a skill that does none of the work itself. It hands every substantive step to something else and spends almost nothing of its own.
  • A worker is a single file addressed to one agent: it is handed a scope, it runs once, and it returns. It has no door — you cannot type it and the model cannot reach for it. That is exactly what lets it carry a model of its own instead of inheriting whatever session called it.
  • Two homes. Sessions and orchestrators are both skills/<name>/SKILL.md — the difference between them is one declaration, not one directory. Workers are workers/<path>.md, and a worker's name carries no family prefix, so its path is what says which family it belongs to.
  • Dispatch is the edge that costs money, and it always resolves into a worker. Three other things look the same in the text and are not dispatches: one skill reading another as its delta, a pipeline naming the next stage, and a pointer placing one skill beside its neighbour.
  • A door on top of a worker dispatches it — it never reads it inline. Read inline, the worker runs at the calling session's tier and the model its own row names selects nothing.

Underneath: the standards

Skills carry procedure. The rules live one layer down.

  • core-principles.md and writing.md — read on every task, by everything.
  • code-style.md, testing.md, architecture/ — read when you touch code.
  • building.md — the loop that takes one settled requirement to a tree where the checks pass.
  • quality-pipeline.md — the review stages, and what each check has to prove before it counts as passed.
  • git.md, records.md, live-systems.md, browser.md — read on their own triggers.

One home per rule

Every rule lives in exactly one file; everywhere else points at it by path. A standard names the job; the skill doing that job binds itself to the name and cites the standard, never the other way round.

That is why the descriptions in the list above read the way they do. A skill's job is to say what it is and what it is not, so anyone choosing between two neighbours has something to choose on.
