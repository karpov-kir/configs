The two families

The prefix is the contract, not a naming habit.

kk-* — works in any repo

Reviewing, building, diagnosing, refining. Nothing about them assumes a particular way of working.

Drop them into any codebase and they hold. They know the shared writing and engineering standards, and nothing about intents, charters or ships.

idsd-* — one workflow, with state on disk

Intent-driven development: plan a feature, build it, review it, archive it.

They keep a .idsd/ directory — charter, intents, records, reports — and every one of them assumes it exists. If your project has no .idsd/, none of these apply to you.

idsd-*  →  kk-*

The dependency runs one way. A workflow skill calls an any-repo one. The reverse would make a skill that works everywhere carry knowledge of a workflow most repos never use — so when an any-repo skill says what it is not, it names the capability rather than the workflow skill that has it.

The intent-driven path

One reactor coordinates the intent set; separate tasks own each feature.

Use idsd-reactor as the central task for coordinating intents and requesting new ones. Bring new work to that task, including requests that arrive while other features are being built. The reactor starts separate tasks for authoring and shipping; the steps below show the work those tasks own.

0

Seed the project idsd-charter

The what and why of the whole project, plus the limits every feature inherits — the response time you will not exceed, the dependency you will not add. Done once, edited rarely.

writes .idsd/charter.md, including its protected Constraints section

1

Say what to build idsd-intent

One feature becomes an ICE — Intent, Context, Expectations. The goal, what it must respect, and the scenarios that show it works; never how to build it. The skill asks you questions until nothing is left open that could change what gets written, then writes the file.

writes .idsd/intents/NNN-slug/intent.md

Every slice is vertical — storage to interface, demonstrable on its own. "The schema", then "the API", then "the screen" gives you three intents nobody can accept, because none of them changes what a user can do.
2

Ship it idsd-ship

The reactor starts a shipping task for each ready intent. You can also use this skill directly for one feature. It writes the intent first if there isn't one, then runs the three stages below in order and stops to ask you before anything is merged.

idsd-build → idsd-qualify → idsd-finalize

3

Build idsd-build

Settles the questions the intent left open, puts the work on its own branch in its own worktree — a second checkout of the same repository, so two features can be built at once without colliding — then codes and tests until the checks pass. The intent's scenarios are what the tests have to show.

branch idsd/NNN-slug · one worktree per intent

4

Review idsd-qualify

A pipeline of review stages — correctness, security where the change touches any, prose, cleanup — each one a separate pass with its own lens. The result is written down as a report, stamped against the exact version of the code it read.

writes the review report · stamps the version it read

5

Finish idsd-finalize

What the feature taught goes up into the project's own records, then the intent moves to the archive. This runs one at a time across the whole repository, because it writes files every feature shares.

merges decisions · archives the intent

This is the only stage that has to wait its turn. Everything that might ask you a question happens before it — a question asked while the turn is held stalls every other feature behind a thread nobody is watching.

Keep coordination in the reactor

One reactor per intent set. Return to it with new requests.

A request without an intent goes to idsd-reactor. It assigns an intent number and starts a separate idsd-intent task to author the ICE, without building it. Answer that task's questions there. It lands the intent on the target branch and reports back to the reactor.

The reactor tracks the new intent's dependencies and starts an idsd-ship task when it is ready within the approved scope. It coordinates live tasks, relays changes that affect siblings, and starts newly unblocked work as each intent lands. The idsd/audit worker checks consistency and derives the build order.

Keep the reactor task available throughout the run. Bring additions and coordination requests back to it; answer feature-specific questions in the task that asks them.

depends-on → parallel

Dependencies decide what runs together; shared files do not. Two features touching the same code still start at once — the overlap is resolved when each one merges. Hold a pair back only when they would be redoing each other's work.

Which door do I use?

Start here. Everything else is reached through one of these.

I don't know which skill applies, or the work crosses several.
kk-foreman — say what you want done and it picks the skills, orders them and runs them. Add unattended to hand it the whole run.
I want one place to coordinate intents and request new ones.
idsd-reactor — keep this task as the coordinator. It starts authoring tasks for new requests and shipping tasks for ready intents, then tracks their reports and dependencies.
I want to plan a feature properly before anyone writes code.
Bring the request to your idsd-reactor task. For standalone authoring, use idsd-intent directly: it questions you, then writes the intent. No charter yet? It offers idsd-charter once.
I want this feature built, reviewed and merged.
idsd-ship — the whole path above, stopping to ask you before the merge. Then idsd-ship done to finish it.
I have a batch of intents and want them all going at once.
Use your idsd-reactor task to choose the milestone and approve the schedule. It starts one shipping task per ready intent and launches the rest as their dependencies land.
Something is broken and nobody knows why.
kk-diagnose — on its own, and before any change exists to review. A skill that reads a diff cannot find a cause nobody has reproduced.
I changed code and want it properly reviewed.
kk-qualify — on its own. It decides which review stages fire and in what order, so you never queue them yourself.
I have a plan or a decision and want the holes found before anyone builds.
kk-grill — on its own. Questions only, round by round, until nothing still open could change what gets written.
The reply I just got was a wall of text.
kk-again — same content, cut to what you must know, decide or do.

End-user skills, in their own words

Generated from each skill's own description, so this list cannot drift from the tree.

The descriptions below are quoted from the skills. A gate is a command that must pass before work continues. A chip starts a follow-up session; clients with task tools create it directly. A merge stamp records that a quality pass ran, for later steps to check.

idsd-*
idsd-build

Implement one ICE intent — settle the gaps it leaves, then build and checkpoint. Use for "build the intent". The ICE-shaped delta over kk-build; archiving is idsd-finalize's, and the end-to-end pipeline idsd-ship's.

takes: intent file (NNN-slug), or omit to choose from the unbuilt ones

idsd-charter

Write or edit .idsd/charter.md — an IDSD project's what & why, including the constraints every intent inherits. Use for "seed the project", "set the project charter", "add a project-wide constraint". The level-0 charter; one feature's intent is idsd-intent's.

takes: the vision, scope or constraint to set, or omit to seed the charter

idsd-finalizeyou type it

Land an already qualified intent through a direct merge or a PR, and archive its records. Use for "finalize the intent" or an explicit final checkpoint. Waits for verified landing; the broader ship lifecycle and throwaway cleanup belong to idsd-ship.

takes: <NNN-slug>

idsd-intent

Author or refine an ICE intent — what to build and why, never how; also owns .idsd/roadmap.md and .idsd/for-agents/language.md. Triggers on "intent", "ICE", "IDSD", "plan a feature/project", "pin down a domain term". The feature level; the project's vision and its inherited constraints are idsd-charter's.

takes: feature/project to plan, or an existing intent to refine

idsd-qualify

Run the quality pipeline over the working tree with a merge stamp. Use for "qualify the changes" inside an IDSD project. The .idsd report layer over kk-qualify — the same pass without a report is that skill's.

idsd-reactor

Coordinate ICE intents through separate owning sessions, launching each as its dependencies land. Use for "build the mvp", "ship these intents in parallel", "start the next wave", and follow-up work in an existing reactor. A standalone intent shipment is idsd-ship's; the order or consistency report alone is the intent-audit worker's.

takes: milestone or intent slugs to build (default: ask which milestone)

idsd-ship

Coordinate an ICE intent through build, qualification and authorized landing. Use for "ship it", "merge this", or "continue the ship". For one checkpoint use idsd-build, idsd-qualify or idsd-finalize; several intents at once belong to idsd-reactor.

takes: <arg> | done [<intent>] | qualify | continue [<intent>] | promote

kk-*
kk-againyou type it

Re-answer the reply you just gave, in the shape it should have had — same content, cut to what the human must know, decide or do. Use when a reply arrives as a wall of prose, a recap of what was done, or a narration of files and steps.

takes: what was wrong with it, or which earlier reply to re-answer (default: the last one)

kk-build

Take a settled requirement to a green tree — place the work, plan the stack and the change, then code, test and gate it. Use for "build this", "implement the ticket". The build loop, not the quality pass that reads the result afterwards (kk-qualify).

takes: the requirement to build — a ticket, an issue, a file holding it, or the ask itself

kk-diagnose

Find the cause of a bug, a flake or a performance regression. Use for "diagnose", "debug this", "why is this failing", "why is this slow", or any report of something broken. Cause-finding from a running system; reading a diff for bugs is kk-qualify's code-review lane, and driving a change's stated scenarios its drive lane.

takes: the symptom, in the words of whoever hit it

kk-edit

The edit lane for authored or revised outward artifacts before approval or delivery, including PR text, commit messages, docs and code comments. Also use for "tighten", "humanize", "de-AI this", or "make this readable". Preserves meaning; ordinary session replies and structured worker returns use writing rules directly. Rule and skill-structure changes belong to their own lanes.

takes: text, file, directory, or git scope such as staged or the changes

kk-foremanyou type it

The front door to the kk-* skills and the installed tool skills — say what you want done and this picks them, orders them, and runs them. Use when the work crosses more than one, when you don't know which applies, when it has to land in another system (a ticket, a page), or for a periodic "what does this repo need?". The idsd-* intent workflow is its own door (idsd-ship).

takes: what you want done, plus "unattended" to hand the run over (default: look at the working tree and recommend)

kk-grill

Grill the user relentlessly about a plan, decision or idea — round by round. Use before anything is built, or on any 'grill' trigger phrase. Questions only, and it writes nothing — a skill that turns a plan into a written spec owns that, and invokes this one to do the asking.

takes: the plan, decision or idea to stress-test

kk-handoff

Write the prompt that hands a piece of work to a fresh session, then start the new task. Use for "hand this off", "spawn a session for this", and before starting a separate task. The receiver holds none of this conversation — not a stage subagent spawned inside this run, and not a quality stage naming the next lane for its caller.

takes: the work to hand off

kk-pr

Work a GitHub PR — draft a pending review, address the review comments and push, or refine the description. Use for "review this PR", "address the review comments", "rewrite the PR description". A PR on GitHub, not local changes (kk-qualify's code-review lane), the working-tree pipeline (kk-qualify), or text you already hold (kk-edit), and it runs the kk-flavor pipeline where the bundled code-review does not.

takes: <review|address-review|refine-description|review-and-address> [PR number, URL, or head branch]

kk-qualify

Run the multi-stage quality pipeline over a change set, in any repo. Use for "qualify the changes", "run a quality pass". Several stages, not one review — one pass over local changes is the code-review lane's, a GitHub PR kk-pr's. A caller that needs the result written down where a later step can check it layers that on top of this one.

takes: [scope: a path, a diff selector, or natural language]

Three kinds of thing, two places they live

The shape underneath every skill above. Written out here; the standards enforce it.

Everything in this ecosystem is one of three kinds, and the difference is worth knowing because it decides what a request costs you.

  • A session is a skill that does the work itself. It holds the thinking, and it runs at the model tier that work needs. It is a session because something about it needs you — it decides with you, or it holds context only that conversation has, or it does something with no undo.
  • An orchestrator is a skill that does none of the work itself. It hands every substantive step to something else and spends almost nothing of its own.
  • A worker is a single file addressed to one agent: it is handed a scope, it runs once, and it returns. It has no door — you cannot type it and the model cannot reach for it. That is exactly what lets it carry a model of its own instead of inheriting whatever session called it.
  • Two homes. Sessions and orchestrators are both skills/<name>/SKILL.md — the difference between them is one declaration, not one directory. Workers are workers/<path>.md, and a worker's name carries no family prefix, so its path is what says which family it belongs to.
  • Dispatch is the edge that costs money, and it always resolves into a worker. Three other things look the same in the text and are not dispatches: one skill reading another as its delta, a pipeline naming the next stage, and a pointer placing one skill beside its neighbour.
  • A door on top of a worker dispatches it — it never reads it inline. Read inline, the worker runs at the calling session's tier and the model its own row names selects nothing.

Underneath: the standards

Skills carry procedure. The rules live one layer down.

  • core-principles.md and writing.md — read on every task, by everything.
  • code-style.md, testing.md, architecture/ — read when you touch code.
  • building.md — the loop that takes one settled requirement to a tree where the checks pass.
  • quality-pipeline.md — the review stages, and what each check has to prove before it counts as passed.
  • git.md, records.md, live-systems.md, browser.md — read on their own triggers.

One home per rule

Every rule lives in exactly one file; everywhere else points at it by path. A standard names the job; the skill doing that job binds itself to the name and cites the standard, never the other way round.

That is why the descriptions in the list above read the way they do. A skill's job is to say what it is and what it is not, so anyone choosing between two neighbours has something to choose on.
