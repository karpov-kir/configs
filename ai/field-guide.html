Field guide

Two families, one tree of instructions

This is a set of skills for Claude Code. Each one is a lane: a single job, with a description that says what it covers and what it deliberately does not. You rarely pick a lane yourself — you go through a door, and the door picks. This page is what the doors know.

The two families

The prefix is the contract, not a naming habit.

kk-* — works in any repo

Reviewing, building, diagnosing, refining. Nothing about them assumes a particular way of working.

Drop them into any codebase and they hold. They know the shared writing and engineering standards, and nothing about intents, charters or ships.

idsd-* — one workflow, with state on disk

Intent-driven development: plan a feature, build it, review it, archive it.

They keep a .idsd/ directory — charter, intents, records, reports — and every one of them assumes it exists. If your project has no .idsd/, none of these apply to you.

idsd-*  →  kk-*

The dependency runs one way. A workflow skill calls an any-repo one. The reverse would make a skill that works everywhere carry knowledge of a workflow most repos never use — so when an any-repo skill says what it is not, it names the capability rather than the workflow skill that has it.

The intent-driven path

Once per project, then a loop per feature. The numbers are the real order.

0

Seed the project idsd-charter

The what and why of the whole project, plus the limits every feature inherits — the response time you will not exceed, the dependency you will not add. Done once, edited rarely.

writes .idsd/charter.md · .idsd/constraints.md

1

Say what to build idsd-intent

One feature becomes an ICE — Intent, Context, Expectations. The goal, what it must respect, and the scenarios that show it works; never how to build it. The skill asks you questions until nothing is left open that could change what gets written, then writes the file.

writes .idsd/intents/NNN-slug/intent.md

Every slice is vertical — storage to interface, demonstrable on its own. "The schema", then "the API", then "the screen" gives you three intents nobody can accept, because none of them changes what a user can do.
2

Ship it idsd-ship

The door you actually type. It writes the intent first if there isn't one, then runs the three stages below in order and stops to ask you before anything is merged.

idsd-build → idsd-qualify → idsd-finalize

3

Build idsd-build

Settles the questions the intent left open, puts the work on its own branch in its own worktree — a second checkout of the same repository, so two features can be built at once without colliding — then codes and tests until the checks pass. The intent's scenarios are what the tests have to show.

branch idsd/NNN-slug · one worktree per intent

4

Review idsd-qualify

A pipeline of review stages — correctness, security where the change touches any, prose, cleanup — each one a separate pass with its own lens. The result is written down as a report, stamped against the exact version of the code it read.

writes the review report · stamps the version it read

5

Finish idsd-finalize

What the feature taught goes up into the project's own records, then the intent moves to the archive. This runs one at a time across the whole repository, because it writes files every feature shares.

merges decisions · archives the intent

This is the only stage that has to wait its turn. Everything that might ask you a question happens before it — a question asked while the turn is held stalls every other feature behind a thread nobody is watching.

Many features at once

Two skills sit above the loop rather than inside it.

Once a project has more than a handful of intents, two questions come up that no single feature can answer: do they still agree with each other, and which of them could be built right now? idsd-audit answers the first and derives the order the second needs; idsd-reactor runs that order, launching a session per feature as its dependencies land. Both are listed with the rest below.

depends-on → parallel

Dependencies decide what runs together; shared files do not. Two features touching the same code still start at once — the overlap is resolved when each one merges. Hold a pair back only when they would be redoing each other's work.

Which door do I use?

Start here. Everything else is reached through one of these.

I don't know which skill applies, or the work crosses several.
kk-foreman — say what you want done and it picks the skills, orders them and runs them. Add unattended to hand it the whole run.
I want to plan a feature properly before anyone writes code.
idsd-intent — it questions you, then writes the intent. No charter yet? It offers idsd-charter once.
I want this feature built, reviewed and merged.
idsd-ship — the whole path above, stopping to ask you before the merge. Then idsd-ship done to finish it.
I have a batch of intents and want them all going at once.
idsd-reactor — one session per feature that is ready, and it starts the rest as their dependencies land.
Something is broken and nobody knows why.
kk-diagnose — on its own, and before any change exists to review. A skill that reads a diff cannot find a cause nobody has reproduced.
I changed code and want it properly reviewed.
kk-qualify — on its own. It decides which review stages fire and in what order, so you never queue them yourself.
I have a plan or a decision and want the holes found before anyone builds.
kk-grill — on its own. Questions only, round by round, until nothing still open could change what gets written.
The reply I just got was a wall of text.
kk-again — same content, cut to what you must know, decide or do.

Every skill, in its own words

Generated from each skill's own description, so this list cannot drift from the tree.

Each line below is the skill's own description, quoted as written — the same text Claude reads when it decides which skill applies. Two words recur in them: a gate is a command that has to pass before the work moves on, and a chip is the button Claude Code offers you to start a follow-up session.

idsd-*
idsd-audit

Audit the .idsd/ intent set for cross-intent consistency, and derive the parallel build order it implies. Use for "audit the intents", "do these intents still hang together", "what order do these build in". The whole set — one intent's own ambiguities are idsd-intent's clarify pass, and running the builds off that order is idsd-reactor's.

idsd-build

Implement one ICE intent — settle the gaps it leaves, then build and checkpoint. Use for "build the intent". The ICE-shaped delta over kk-build; archiving is idsd-finalize's, and the end-to-end pipeline idsd-ship's.

takes: intent file (NNN-slug), or omit to choose from the unbuilt ones

idsd-charter

Write or edit .idsd/charter.md — an IDSD project's what & why — and .idsd/constraints.md, the thresholds every intent inherits. Use for "seed the project", "set the project charter", "add a project-wide constraint". The level-0 files; one feature's intent is idsd-intent's.

takes: the vision, scope or constraint to set, or omit to seed both files

idsd-finalizeyou type it

Merge one built intent's records into the project's, then archive it. Use for "finalize the intent". The pipeline's fourth stage, after idsd-qualify — idsd-ship's done invokes it.

takes: <NNN-slug>

idsd-intent

Author or refine an ICE intent — what to build and why, never how; also owns .idsd/language.md. Triggers on "intent", "ICE", "IDSD", "plan a feature/project", "pin down a domain term". The feature level; the project's vision and its inherited constraints are idsd-charter's.

takes: feature/project to plan, or an existing intent to refine

idsd-qualify

Run the quality pipeline over the working tree with a merge stamp. Use for "qualify the changes" inside an IDSD project. The .idsd report layer over kk-qualify — the same pass without a report is that skill's.

idsd-reactor

Build several ICE intents at once — one session per unblocked intent, launching each as its dependencies land. Use for "build the mvp", "ship these intents in parallel", "start the next wave". One intent end-to-end is idsd-ship's, and the order or the consistency report on its own is idsd-audit's.

takes: milestone or intent slugs to build (default: ask which milestone)

idsd-ship

Ship one ICE intent end-to-end — author it if missing, build, qualify, gate, merge — or review standalone changes. Use for "ship it", "merge this", "continue the ship". The orchestrator above idsd-build, idsd-qualify and idsd-finalize; several intents at once is idsd-reactor's.

takes: <arg> | done [<intent>] | qualify | continue [<intent>] | promote

kk-*
kk-againyou type it

Re-answer the reply you just gave, in the shape it should have had — same content, cut to what the human must know, decide or do. Use when a reply arrives as a wall of prose, a recap of what was done, or a narration of files and steps.

takes: what was wrong with it, or which earlier reply to re-answer (default: the last one)

kk-build

Take a settled requirement to a green tree — place the work, plan the stack and the change, then code, test and gate it. Use for "build this", "implement the ticket". The build loop, not the quality pass that reads the result afterwards (kk-qualify).

takes: the requirement to build — a ticket, an issue, a file holding it, or the ask itself

kk-code-review

Review the working-tree changes for correctness bugs — apply the safe fixes, surface the rest. Use for "code review". One pass, not a pipeline (kk-qualify); a GitHub PR is kk-pr-review's; style is kk-refactor's lane, vulnerabilities kk-security-review's. Judges against the kk-flavor standards, unlike the same-named bundled reviewer.

takes: file, directory, diff selector (staged/unstaged/all changed), or natural-language scope

kk-conform

Check a change set against the ask it was given — every requirement delivered, nothing beyond them, and no contradiction inside it. Use for "does this match the requirements". Judged by reading, never by running (kk-drive); needs the ask in hand, where kk-code-review needs none.

takes: the requirement set, plus the change set to judge against it

kk-diagnose

Find the cause of a bug, a flake or a performance regression. Use for "diagnose", "debug this", "why is this failing", "why is this slow", or any report of something broken. Cause-finding from a running system; reading a diff for bugs is kk-code-review's, and driving a change's stated scenarios is kk-drive's.

takes: the symptom, in the words of whoever hit it

kk-drive

Use a change the way its user will and report each scenario's observed outcome with its evidence. Use for "drive it", "does this actually work?", "verify it end to end". A quality pass's drive gate, bound by rules a plain start-the-app-and-show-me is not. Observed runtime behaviour, never code read (kk-code-review) or a gate's green.

takes: the scenarios to drive, plus how to run the project

kk-foremanyou type it

The front door to the kk-* skills and the installed tool skills — say what you want done and this picks them, orders them, and runs them. Use when the work crosses more than one, when you don't know which applies, when it has to land in another system (a ticket, a page), or for a periodic "what does this repo need?". The idsd-* intent workflow is its own door (idsd-ship).

takes: what you want done, plus "unattended" to hand the run over (default: look at the working tree and recommend)

kk-grill

Grill the user relentlessly about a plan, decision or idea — round by round. Use before anything is built, or on any 'grill' trigger phrase. Questions only, and it writes nothing — a skill that turns a plan into a written spec owns that, and invokes this one to do the asking.

takes: the plan, decision or idea to stress-test

kk-handoff

Write the prompt that hands a piece of work to a fresh session, then create the chip that starts it. Use for "hand this off", "spawn a session for this", and before creating a background-task chip for any reason. The receiver holds none of this conversation — not a stage subagent spawned inside this run, and not a quality stage naming the next lane for its caller.

takes: the work to hand off

kk-humanize

Rewrite outward text — PR/ticket text, commit messages, chat, email, README-grade docs — and code comments so they read as a person wrote them. Use for "humanize", "de-AI this", "make the comments readable". The outward counterpart to kk-tighten; comment placement and truth belong to other lanes.

takes: file, git scope ("the changes", "staged"), or the text itself

kk-pr-review

Review a GitHub PR — a pending review to draft, or, with the fix token and always on your own PR, fixes to apply and push. Use for "review this PR" and "address the review comments". A PR on GitHub, not local changes (kk-code-review) or the working-tree pipeline (kk-qualify), and it runs the kk-flavor pipeline where the bundled code-review does not.

takes: <PR number, URL, or head branch> [fix]

kk-qualify

Run the multi-stage quality pipeline over a change set, in any repo. Use for "qualify the changes", "run a quality pass". Several stages, not one review — one pass over local changes is kk-code-review's, a GitHub PR kk-pr-review's. A caller that needs the pass written down with a merge stamp layers that on top of this one.

takes: [scope: a path, a diff selector, or natural language]

kk-refactor

Review files against the kk-flavor standards and refactor them into compliance, hunting duplication and simplification across the codebase. Use for "refactor" or "clean up". Quality, not correctness (kk-code-review), vulnerabilities (kk-security-review), or prose concision (kk-tighten).

takes: file, directory, diff selector (staged/unstaged/all changed), whole project, or natural-language scope

kk-retroyou type it

Adversarial retrospective on how a run was conducted, never the change it produced. Only the human starts one, after a run that went badly, went oddly, or went well enough to be worth knowing why.

takes: the run or session to reflect on

kk-security-review

Adversarially review the working-tree changes for exploitable vulnerabilities. Use for "security review", "audit the changes for vulns". Local changes; a GitHub PR is kk-pr-review's, functional bugs kk-code-review's. Works this skill's own threat model, unlike the same-named bundled reviewer.

takes: file, directory, diff selector (staged/unstaged/all changed), or natural-language scope

kk-tighten

Tighten internal prose — docs, skills, standards, prompts — for the context window, cutting redundancy and inferable filler. Triggers on "tighten", "shrink", "de-duplicate". Outward text and code comments are kk-humanize's; refining a whole instruction tree is kk-ecosystem's, which runs this last.

takes: file, directory, or natural-language scope (e.g. "the changes", "staged")

Underneath: the standards

Skills carry procedure. The rules live one layer down.

  • core-principles.md and writing.md — read on every task, by everything.
  • code-style.md, testing.md, architecture/ — read when you touch code.
  • building.md — the loop that takes one settled requirement to a tree where the checks pass.
  • quality-pipeline.md — the review stages, and what each check has to prove before it counts as passed.
  • git.md, records.md, live-systems.md, browser.md — read on their own triggers.

One home per rule

Every rule lives in exactly one file; everywhere else points at it by path. A standard names the job; the skill doing that job binds itself to the name and cites the standard, never the other way round.

That is why the descriptions in the list above read the way they do. A skill's job is to say what it is and what it is not, so anyone choosing between two neighbours has something to choose on.
