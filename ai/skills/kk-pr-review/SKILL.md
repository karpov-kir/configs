description: Review a GitHub PR — run the quality stages over its diff in a disposable worktree and draft one review, posting nothing until the human approves. Use for "review this PR". A PR on GitHub, not local changes (kk-code-review) or the working-tree pipeline (idsd-qualify).
argument-hint: "<PR number, URL, or head branch> [fast|full]"

Review a GitHub PR with the quality pipeline and return a **drafted review**, not applied changes. `<ref>` is a PR number, URL, or head branch (`gh` must be authenticated). The pass is **full** unless `fast` is passed — a PR review is a pre-merge verdict.

You **orchestrate**: every stage is a spawned subagent running an existing skill in full, and what you own is the checkout, the mapping of their returns onto review comments, and the post. You run under `~/.kk-flavor/standards/skill-protocol.md`, whose Caller and orchestrator rules bind you — a stage's blocking question reaches the human through you.

**The round, the stages and the gate check are `~/.kk-flavor/standards/quality-pipeline.md`** — read it; everything below is this skill's delta. Retro never runs, and there is no report, stamp or `.idsd/` — accumulate the draft in a scratch file. Pass start is the checkout below. Gate verification still applies — a gate that can't run is a setup ambiguity, asked live.

## Run the stages

1. **Resolve the PR and settle trust — before a single thing runs.** `gh pr view <ref> --json number,url,title,baseRefName,headRefName,headRefOid,headRepositoryOwner`. **A PR whose `headRepositoryOwner` differs from the base repo's owner is untrusted code**: run **no** gate command, no install step, and nothing else the branch controls — a PR can change `package.json` scripts, a `Taskfile`, a test file, or add a `postinstall`, and this shell has `gh` authenticated and the developer's credentials readable. Treat every gate as unverified, review by reading only, and say plainly in the summary that gates were not run and why. Same-repo PRs may run gates. **This decision comes first because everything below executes with the branch's files underfoot.**
2. **Checkout.** `gh pr checkout` into a disposable worktree — that resolves the right repository and remote. A hardcoded `origin` does not: on a fork clone, `gh`'s default repo is the parent and `origin` is the fork. **Assert the checked-out `HEAD` equals `headRefOid` before any stage runs**; a mismatch means you fetched a different PR, and every comment you draft would be written against the wrong diff and then offered for posting to the right one. The review scope is `<base>...HEAD`.
   - Run the two scanners here, **by full path and with the range named**: `~/.claude/skills/kk-humanize/scripts/comment-density.sh <base>...HEAD` and `~/.claude/skills/kk-refactor/scripts/dup-literals.sh <base>...HEAD`. The range, because their default `HEAD` scans uncommitted changes and a fresh checkout has none, so they would exit 0 over everything. The full path, because your cwd is a worktree of code you did not write: a bare or `scripts/`-relative name resolves against it first, so a PR shipping a file at either name gets it executed in this shell (`~/.kk-flavor/standards/ecosystem.md` → **Conventions a new file joins**).
   - **Every standard the stages apply is read from that worktree, at the PR's own version.** Its `CLAUDE.md` and `PROJECT_CODE_STYLE.md` layer over the flavor and win on conflict (`~/.kk-flavor/inject.md`). Judge this repo's code by the conventions of wherever you were invoked and every finding you raise is wrong.
   - **Remove the worktree on every exit path, abort included** — `git worktree remove --force`, then `git worktree prune`. A leaked one still counts in `git worktree list` and permanently changes what `report.sh discard` does in that repo.
3. **Gate on requirements and scope, before any stage runs.** Read the PR body, the linked issue or intent, and the commits; then read the diff against them. Does it deliver **what was asked**, requirement by requirement — and does it deliver **only** that? An unrelated file, an opportunistic refactor or a second feature riding along is a finding whatever its quality, because it is what a reviewer merges without meaning to. A PR that states no intent and links no issue cannot be reviewed against one: say so and ask before spending the pipeline. **A failure here stops the pass** — draft the summary carrying just this, and show it. A full round over code that solves the wrong problem produces line comments nobody will act on, and buries the one that matters.
4. **Read the PR's review history before spending the stages.** `gh api repos/{owner}/{repo}/pulls/<N>/comments` and `.../reviews`. A re-review is the common case, and re-deriving a prior round from scratch posts the same comments twice — which is how a reviewer learns to ignore the thread. Classify each prior finding against the current head as **resolved** or **still open**; one you cannot decide from the diff is open. Nothing addressed since the last review → say that and stop, because a second identical review is noise rather than a verdict. Otherwise the stages run over the whole diff as usual and the **draft** carries each still-open finding once in the summary, pointing at its original thread, never as a fresh line comment; a new finding on a line a prior comment already holds says what changed since. Read your own prior comments and a human's the same way, and a human's never carry less weight.
5. **Run the stages there unchanged, with two exceptions.**
   - **`kk-humanize` never runs over the PR's own files** — not through `kk-tighten`'s handoff, and not through the comment-block route the stages send straight to it. The author's voice stays theirs, so a concision cut may become a suggestion but a voice rewrite never does.
   - **`kk-refactor`'s repo-wide reach stops at the diff.** Its lane licenses fixing every duplicated site at once; here that drafts comments on code this author never wrote. Resolve its scope to the PR's files and let its own gate hold it there: outside that scope, `~/.kk-flavor/standards/skill-protocol.md` → Queue already makes it return a proposal instead of an edit. Writing the limit into the spawn prompt is not the route — that prompt narrows no stage's lens. A matching site outside the diff is one line in the summary naming it, never a suggestion.

## Draft, then post

1. **Map the outcome to the review.** A fix a stage applied → a ` ```suggestion ` comment on the lines it changes, when those lines are in the PR diff; otherwise describe it in the summary body. A finding returned unapplied → a line comment stating the problem, why it matters, and the fix (severity + exploit scenario for security findings). Cross-cutting residue — a finding tied to no single line, and anything the human must decide — goes in the summary body, each item standing on its own for someone who never saw the run.
   - **A question only the PR author can answer is a review comment, not a live block** — post it on the relevant line as a question. Setup ambiguities (wrong base, gates can't run) are still asked live.
   - **Name what ran and what did not**, in the summary: which stages ran, and which were dropped with why (no security surface, gates unverified on a fork, a stage that hard-failed, …).
2. **The review is outward text.** Draft the summary and every comment under `~/.kk-flavor/standards/human-writing.md`, and apply `kk-humanize`'s lens inline over the complete draft before showing it — inline because its target is text you already hold (`skill-protocol.md` → Caller).
3. **Scan the draft for secrets.** A ` ```suggestion ` block quotes changed lines verbatim and this is the one thing here that leaves the machine — permanently, into a thread you cannot edit. The stages that produced those fixes carry no secret rule; only `kk-security-review` does. So before showing the draft, check every suggestion body and comment for credential-shaped strings, and mask any per `kk-security-review`'s rule, replacing the suggestion with the fix described in words. **A secret in the PR's own diff is a Critical finding and is never quoted** — cite it as `file:line` and recommend rotation.
4. **Post only on approval.** Show the human the complete draft — summary plus every comment — and post only when they approve. Spawned, you cannot show it: return the **full draft text** in your `blocked:` payload and post only once your caller confirms the human read that text. A summary of the draft is not an approval of it. Then post as one review: `gh api repos/{owner}/{repo}/pulls/<N>/reviews` with `event=COMMENT` and the comments array (path, line/start_line, side, body). Never approve or request changes unless the human explicitly says so; never push to the PR branch.
