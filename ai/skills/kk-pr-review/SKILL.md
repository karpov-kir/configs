argument-hint: "<PR number, URL, or head branch> [fast|full]"

Return a **drafted review** over `<ref>`, never applied changes; `gh` must be authenticated. The pass is **full** unless `fast` is passed — a PR review is a pre-merge verdict.

You **orchestrate**: every stage is a spawned subagent running an existing skill in full, and what you own is the checkout, the drive, the **selection** of their returns into a review, and the post. You run under `~/.kk-flavor/standards/skill-protocol.md` — a blocking question from a stage or from the drive reaches the human through you.

**The round, the stages and the gate check are `~/.kk-flavor/standards/quality-pipeline.md`** — read it; everything below is this skill's delta. Retro never runs, and there is no report, stamp or `.idsd/` — collect the stage returns in a scratch file. **That file is raw material, not a draft-in-progress** — the review gets written once, at **Draft, then post**. A gate that can't run is a setup ambiguity, asked live.

## Set up, gate, drive, then run the stages

1. **Resolve the PR and settle trust — before a single thing runs.** `gh pr view <ref> --json number,url,title,baseRefName,headRefName,headRefOid,headRepositoryOwner,author`. **A PR whose `headRepositoryOwner` differs from the base repo's owner is untrusted code**: run **no** gate command, no install step, and nothing else the branch controls — a PR can change `package.json` scripts, a `Taskfile`, a test file, or add a `postinstall`, and this shell has `gh` authenticated and the developer's credentials readable. Treat every gate as unverified, review by reading only, and say plainly in the summary that gates were not run and why. Same-repo PRs may run gates. **Everything below executes with the branch's files underfoot.**
2. **Checkout.** `gh pr checkout` into a disposable worktree — that resolves the right repository and remote. A hardcoded `origin` does not: on a fork clone, `gh`'s default repo is the parent and `origin` is the fork. **Assert the checked-out `HEAD` equals `headRefOid` before any stage runs**; a mismatch means you fetched a different PR, and every comment you draft would be written against the wrong diff and then offered for posting to the right one. The review scope is `<base>...HEAD`.
   - Run the two scanners here, **by full path and with the range named**: `~/.claude/skills/kk-humanize/scripts/comment-density.sh <base>...HEAD` and `~/.claude/skills/kk-refactor/scripts/dup-literals.sh <base>...HEAD`. The range, because their default `HEAD` scans uncommitted changes and a fresh checkout has none, so they would exit 0 over everything. The full path, because your cwd is a worktree of code you did not write: a bare or `scripts/`-relative name resolves against it first, so a PR shipping a file at either name gets it executed in this shell (`~/.kk-flavor/standards/ecosystem.md` → **Conventions a new file joins**).
   - **The stages read this repo's own standards from that worktree, at the PR's version** — its `CLAUDE.md` and `PROJECT_CODE_STYLE.md` (`~/.kk-flavor/inject.md`). Judge this repo's code by the conventions of wherever you were invoked and every finding you raise is wrong.
   - **Remove the worktree on every exit path, abort included** — kill whatever the drive started first, then `git worktree remove --force` and `git worktree prune`. A dev server outlives the removal holding its port, and the next review drives against it and observes the wrong branch. A leaked worktree still counts in `git worktree list` and permanently changes what `report.sh discard` does in that repo.
3. **Gate on requirements and scope.** Read the PR body, the linked issue or intent, and the commits; then read the diff against them. Does it deliver **what was asked**, requirement by requirement — and does it deliver **only** that? An unrelated file, an opportunistic refactor or a second feature riding along is a finding whatever its quality, because it is what a reviewer merges without meaning to. A PR that states no intent and links no issue cannot be reviewed against one: say so and ask before spending the pipeline. **A failure here stops the pass**: draft a review carrying just this, post it under **Draft, then post**, and stop — the author resolves a wrong-problem PR before the rest is worth spending, and the thread is where that resolution happens.
4. **Read the PR's review history before spending the stages** — `gh api repos/{owner}/{repo}/pulls/<N>/comments` and `.../reviews`. Re-deriving a prior round from scratch posts the same comments twice, which is how a reviewer learns to ignore the thread. **With no prior round, the bullets below do not apply** — a first review has addressed nothing by definition and never stops on it.
   - **Classify each prior finding against the current head** as **resolved** or **still open**; one you cannot decide from the diff is open. Read your own prior comments and a human's the same way, and a human's never carry less weight.
   - **Nothing addressed since the last review → say that and stop.** But **a review whose comments you deleted is not one that stands**: where the last round was your own withdrawal, that stop does not fire, and the replacement is drafted from the diff rather than from what you deleted.
   - Otherwise the stages run over the whole diff as usual, and the **draft** carries each still-open finding as one body line pointing at its original thread, never as a fresh line comment. A new finding on a line a prior comment already holds says what changed since.
   - **A prior finding the head resolved gets no mention at all**, including one you checked and found correctly dismissed.
5. **Drive the change in the worktree before the stages read it** — `~/.kk-flavor/standards/quality-pipeline.md` → **Drive it before you review it**, with the deltas that follow. Its scenarios are the ones step 3 read. **An untrusted PR is never driven** — step 1 bars running what the branch controls, and a drive is exactly that. Never ask the human to waive that; fold the skip into step 1's unverified-gates sentence. That skip is the fork's alone. And **what the drive surfaces stops the pass the way step 3 does.**
6. **Run the stages there unchanged, with two exceptions.**
   - **`kk-humanize` never runs over the PR's own files** — not through `kk-tighten`'s handoff, and not through the comment-block route the stages send straight to it. The author's voice stays theirs, so a concision cut may become a suggestion but a voice rewrite never does. **Theirs, not yours.** Compare the `author` login from step 1 to the account `gh` is authenticated as (`gh api user --jq .login`). Where they match, the voice being protected is your own. The bar does not bind, and the PR's body is prose like any other.
   - **`kk-refactor`'s repo-wide reach stops at the diff.** Its lane licenses fixing every duplicated site at once; here that drafts comments on code this author never wrote. Resolve its scope to the PR's files and let its own gate hold it there: outside that scope, `~/.kk-flavor/standards/skill-protocol.md` → Queue already makes it return a proposal instead of an edit. Writing the limit into the spawn prompt is not the route — that prompt narrows no stage's lens. A matching site outside the diff is not posted at all (**Draft, then post**).

## Draft, then post

1. **Select, don't transcribe.** The review is outward text, and the bar for what earns a comment and the shape of one is `~/.kk-flavor/standards/human-writing.md` → **Review comments** — read it now, before you draft a line; everything below is only what GitHub and the pipeline add. A finding that fails that bar is **dropped, never relegated to the body** — not lost: it reaches the human in your closing reply, who decides what becomes its own change.
   - **The defect, then the fix, in two or three sentences.** A ` ```suggestion ` block replaces that prose when the fix is code on the diff's own lines. Severity and an exploit scenario stay on a security finding.
   - **The body is the mergeable-or-not verdict in a sentence or two, plus only what the steps above place there**: the gate's requirement or scope mismatch, what the drive surfaced, each still-open prior finding, and **what the review could not check, which the verdict rests on** — an untrusted PR's unverified gates, a needed drive that did not run and why. Nothing else — a finding that fits no single line goes on the closest line it concerns, or to the human. No stage list.
   - **Nothing outside the diff is posted** — a duplicated site elsewhere, a gated proposal, a pre-existing defect. Those are for the human, not the thread.
   - **A question only the PR author can answer is a line comment, not a live block.** Setup ambiguities (wrong base, gates can't run) are still asked live.
2. **Humanize the draft.** Apply `kk-humanize`'s lens inline over the complete draft before showing it — inline because its target is text you already hold (`skill-protocol.md` → Caller).
3. **Scan the draft for secrets.** A ` ```suggestion ` block quotes changed lines verbatim and this is the one thing here that leaves the machine — permanently, into a thread you cannot edit. The stages that produced those fixes carry no secret rule; only `kk-security-review` does. So before showing the draft, check every suggestion body and comment for credential-shaped strings, and mask any per `kk-security-review`'s rule, replacing the suggestion with the fix described in words. **A secret in the PR's own diff is a Critical finding and is never quoted** — cite it as `file:line` and recommend rotation.
4. **Post only on approval.** Show the human the complete draft — summary plus every comment — and post only when they approve. Spawned, you cannot show it: return the **full draft text** in your `blocked:` payload and post only once your caller confirms the human read that text. A summary of the draft is not an approval of it. Then post as one review: `gh api repos/{owner}/{repo}/pulls/<N>/reviews` with `event=COMMENT` and the comments array (path, line/start_line, side, body). Never approve or request changes unless the human explicitly says so; never push to the PR branch.
