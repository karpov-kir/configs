Run the quality stages over one change set and leave only the residue that needs the human. You **orchestrate** existing skills — invoke them, never reimplement; their rules still hold (gates absolute, no-mocks, …). Callers: standalone, or `idsd-ship` running its quality pass — which invokes this skill **inline**, never as a subagent: this skill spawns the stage subagents and relays their pauses to the human, and nesting it would put two hops on every relay.

**Interactive first.** The orchestrator rule in `~/.kk-flavor/standards/skill-protocol.md` applies: a decision you can't settle from the code, the intent, or a sensible default is *blocking* — asked live, with a recommended answer earned by legwork; a subagent's `blocked` relays with its recommendation and is answered and **resumed by ID**, never respawned. The report is for what does *not* block — never a place to park a question you should ask.

**kk-flavor wiring.** If the flavor isn't injected, read `~/.kk-flavor/inject.md` first, and read `~/.kk-flavor/standards/skill-protocol.md` (the orchestrator rule above, and the contract the stage subagents run under). The stage names below (`/code-review`, `/security-review`, `/refactor`, `/tighten`) are **roles** — spawn the skill mapped in `~/.kk-flavor/config.yaml` → `roles` (unlisted names resolve to themselves; the quality roles default to the `kk-` variants). Run a stage only when its `config.yaml` → `pipeline` flag is true — a stage turned off is **skipped silently** (don't spawn it, don't record its absence as a gap). Code-review is structural and always runs.

## Modes and targets

| Invocation | Mode | Target |
|---|---|---|
| `idsd-qualify` / `idsd-qualify fast` | fast | working tree |
| `idsd-qualify full` | full | working tree |
| `idsd-qualify pr <ref> [fast\|full]` | full unless overridden | a GitHub PR (see **PR target**) |

**Fast is the iteration mode** — the edit→qualify loop while the change is still moving; it trades refactor's completeness loop and retro for turnaround. It is an iteration tool, not a verdict. **Full is the verdict** — the pass that must precede a merge: `idsd-ship <intent>` runs it as its pipeline pass, `idsd-ship done` refuses to merge on a turnaround-trimmed stamp, and a PR review defaults to it.

Both modes run the same parallel round: code-review always; security-review when the change touches a security surface; tighten when prose changed. The modes differ after the round — **fast** runs refactor once, and retro only if the human course-corrected, the run touched its own tooling, or the human asks; **full** loops refactor to compliance (cap per its stage) and always ends with retro (never on a PR target).

## Running a pass (working-tree target)

Always run `scripts/report.sh check-ignore` (in this skill's dir) before anything else — it keeps the report out of the fingerprint by the mechanism that fits the repo's mode (see **Report**). The script resolves the repo from the shell's cwd, and `init` prints the full path it created — confirm that path is the change set's repo before proceeding; a mismatch means the cwd drifted (one run initialized `.idsd/` in a sibling repo that way). Then start from the right base: **first pass on a change set** (no report, or one recording a different intent) — scaffold with `report.sh init "<intent-or-description>"`; when `idsd-ship` already initialized it for this change set (it records build-stage items before qualifying), that's the same report — keep appending. **Re-qualify** — keep the report and reconcile per the carry rule (**Structure**, below); `report.sh carry` lists the prior open `- [ ]` so none are lost. Either way, run `report.sh invalidate` once the base is set: it clears the previous `reviewed-tree` so a stamp cannot outlive the tree it describes while this pass edits files (a pass that changed nine files left the prior round's stamp standing for its whole duration, and the merge gate reads that stamp).

**The parallel round.** Spawn the round's stages **in one message** so they run concurrently: code-review always, plus security-review and tighten when their conditions and pipeline flags admit them. Concurrent writers on one tree are safe here only because the round is write-light and lane-disjoint: code-review applies targeted correctness fixes, security-review only trivial safe ones, tighten only prose. Collisions are therefore rare, and a stage whose edit lands on a file that changed underneath re-reads and reapplies. Record each stage's items the moment that stage returns, not batched at the end of the pass — and make that mechanical rather than remembered: **the first thing you do with any stage's return is `report.sh stage-returned <stage>`, before reading its findings**, then record. `stamp` refuses while a marker is newer than the report, so a stage whose items were never written down cannot be stamped over. Marking after you have already edited the report defeats it — the marker is then the newer file and the stamp blocks on work you did do.

**Refactor is the round's serializer, and the round must have settled *to a decision* before it spawns.** It runs after the round as a fresh spawn over the now-changed tree, never joining it, for two reasons: its method (re-read everything, catch what only surfaces after earlier fixes land) needs the others' output already in the tree, and it is the heaviest writer. Settled means every blocking finding the round returned is *answered and applied*, not merely returned — ask the human the moment a stage hands you one rather than batching it with refactor's own proposals. A correctness fix landing after refactor has run is the expensive path: it invalidates the tree the serializer just read, and typically widens the change set, forcing a fresh refactor iteration and a tighten re-run from scratch.

**The comment pass runs once, after refactor — and it's humanize's alone.** Split the prose concern by artifact kind: standalone prose (docs, markdown) joins the parallel round via `/tighten`, because no later stage rewrites it; **comment blocks wait** — refactor renames the identifiers comments name and authors new doc blocks of its own, so any earlier pass over them is discarded work whose only lasting effect is a collision with code-review on the same file. And they get one subagent, not two: humanize's comment form (`human-writing.md`) subsumes tighten's lossless cuts on comments, so spawning tighten first is paying twice for the same pass. On a change set that is only code, nothing prose-related joins the round.

**How each stage runs.** The stages are mostly autonomous, returning findings as data with an occasional `blocked`, so each runs in a **dedicated subagent** (which also isolates its heavier context from the orchestrator). The subagent executes the skill in full and returns structured findings; it never decides whether to run, and never fakes the pass with its own inline judgment. Only the main thread has the human, so every decision and all report-writing stay here: take the returned findings, ask the human live for any that block, record the rest. When a subagent pauses with `blocked: <what it needs>`, answer it and resume it by ID (per the protocol).

**Spawn the skill, not your own review.** Build each subagent prompt from `templates/spawn-prompt.md` (this skill's dir; the retro stage from `templates/retro-spawn-prompt.md`) — its only slots are the skill name, the change scope, emphasis the **user explicitly stated** this run (verbatim), and deterministic tool output (e.g. `dup-literals.sh` hits) passed verbatim as evidence. Nothing else goes in. The skill defines what to check; the spawn prompt must not pre-select, narrow, or invent which rules apply, must not borrow another stage's lane (correctness is `/code-review`'s, style/structure/architecture is `/refactor`'s, vulnerabilities are `/security-review`'s, prose/concision is `/tighten`'s), and must let the subagent run the skill's full decomposition itself. A lead you inferred is not emphasis and not evidence — a spawn prompt that lists specific CLAUDE.md rules to look for, or asks for findings outside the named skill's scope, is the defect this guards against.

**A script's output is evidence only when the script ran.** The evidence scripts exit 0 clean, 1 with hits, 2 when git rejected their arguments — read anything but 0 or 1 as *no evidence*, and either fix the invocation or say plainly that the scan did not run. They take **git-diff arguments, not paths**: `dup-literals.sh origin/main`, never the output of `git diff --name-only`. An exit you did not look at must never reach a spawn prompt as "returned no hits" — one run handed refactor exactly that after git had refused the arguments and the scan had never happened.

**Fixes you apply between the round and refactor are unreviewed code, and the round is not settled until they are reviewed.** When a stage returns a finding it is not licensed to fix and the human's answer lands in your hands, you become the author — and refactor (style) and the comment pass (prose) are the only stages that follow, so nothing looks at the correctness of what you wrote. Spawn one fresh `/code-review` scoped to just the files those answers changed, before refactor. The cost is one extra subagent on any pass with post-round fixes; the case for paying it is a pass that authored 269 lines this way and shipped a branch with no test, which its own retro then had to catch.

**Reconcile contradictions.** When two stages give opposing verdicts on the same location — one clears what another flags — or a claim contradicts an observation (a subagent reports green while a tool shows otherwise), adjudicate empirically before recording: re-run the check yourself and trust neither side's word over the result.

**Scale to the change; settle design once.** Match review weight to the delta — a small, low-risk change doesn't need every stage's full fan-out, a broad or risky one does; scope each subagent to the changed surface rather than re-running the world (scoping narrows *files*, never *rules* — **Spawn the skill, not your own review** holds regardless). And when a change reworks a **shared or cross-repo primitive** (a vendored arch primitive, a public type, a cross-cutting contract), settle its target shape with the human in one pass *before* iterating — converging a design through many one-finding-at-a-time review round-trips is the most expensive path.

### The stages

1. **Code-review** — spawn a subagent to run `/code-review` on the change set: it applies every fix it can make correctly and returns the rest — findings needing a human decision (a trade-off, an ambiguous intent, a risky change), plus any behaviour-changing fix it made. On its return, ask the human live for blocking findings; record the others.
   - Record as **Decide** items: findings needing a human decision. A fix already applied is recorded only if the human might want to reverse it (ratify-or-revert); otherwise it's just the diff.
2. **Security-review** — *only if* the change touches a security surface (input handling, filesystem/network/exec, auth or session, secrets, deserialization, or any constitution security invariant — a trigger summary; the coverage set is the skill's); otherwise skip. Spawn a subagent to run `/security-review` on the change set: it applies trivial safe fixes (e.g. secret redaction) and returns the rest as findings with severity, exploit scenario, and fix. On its return, ask the human about anything blocking; record the others.
   - Record as **Decide** items: findings needing a human decision (severity + exploit + fix). Record nothing when the surface was clean or untouched.
3. **Tighten & comment pass** — *only if* the change added or changed standalone prose (docs, markdown) or non-trivial comment blocks; otherwise skip. One prose concern, two passes — both stamp under the `tighten` entry, and the `pipeline` → `tighten` flag governs both. **Standalone prose** is the change set's prose *plus the prose this pass itself wrote* — the intent above all, which lives outside git in throwaway mode and so appears in no diff you can resolve a scope from; name those files explicitly in the spawn prompt's scope slot. Spawn `/tighten` in the round; it applies the lossless cuts and returns only what it couldn't safely cut (a doubtful-substance cut, an unresolved `WARN`) — record that remainder; when its return notes an outward-text handoff (`human-writing.md`'s set — README-grade docs and similar), spawn the `humanize` role over those files as part of this stage. **Comment blocks**: run `scripts/comment-density.sh` over the change set, then spawn `humanize` directly, after refactor (its comment form, per **The comment pass** above — no tighten first), with density outliers riding the spawn prompt's tool-output slot; it applies its safe rewrites and returns doubtful cuts and parked substance.
   - Record as a **Decide** item only what either pass flagged but couldn't safely resolve; nothing otherwise.
4. **Refactor** — in full mode a loop (max 3 iterations), the pipeline's safety net for completeness — don't shortcut it; in fast mode a single iteration — speed over the completeness net. Before the first iteration, run `scripts/dup-literals.sh` (this skill's dir) over the change set; any hits ride the spawn prompt's tool-output slot — deterministic output is evidence, not an inferred lead. Run it **again after the last iteration**: refactor rewrites call sites, so it authors duplication of its own that a pre-stage scan cannot see (one run's only real hit was a three-times-repeated assertion refactor had just created). Hits from that second run are yours to resolve or record, not a reason to spawn another iteration. Each iteration spawns a **fresh** subagent (not a resume) to run `/refactor` on the changes: it applies routine fixes, returns gated architecture/testing/project-setup ones as proposals (not applied), and reports whether the change is now fully compliant. Spawning fresh re-reads the now-changed tree, catching fixes that only surface after earlier ones land. Stop the moment a subagent reports compliant; otherwise iterate to the cap. The blocked→resume rule still holds *within* an iteration — only a new iteration spawns fresh. On each return, ask the human about gated proposals; record what's deferred or declined.
   - Record: gated fixes the human must rule on (**Decide**), duplication deferred under the extract threshold (**Watch**), and — if it hit the cap without reaching compliant — that, with what's open (**Decide**). Nothing when it reached compliant with no gated proposal.
5. **Retro** — per **Modes and targets**; always last. Write a terse, factual run-log — what was asked, what each stage did, where the human corrected course, what was deferred. **This numbering is not the execution order:** stage 3's comment pass runs after stage 4, so write the log only once that pass has returned, and name it among the stages. A log written when stage 3 is first reached silently omits a stage that edited files, and since the log is the retro's authoritative input, everything that stage touched becomes a blind spot — observed: a comment pass rewrote five files and re-staled an already-redeployed image *after* the log was written, so the retro could only report it as a risk to re-verify rather than a finding. State a defect the run hit and how it surfaced, since the retro would otherwise rediscover it, but as an event: never grade the run, draw its conclusion, or frame what a stage "should" have caught — a log that has judged itself invites the retro to agree rather than look. For anything that appears in no diff — server state above all — record the observation rather than the inference: the command and what it printed, not the conclusion you drew from it, which the retro has no way to check. Name or point at each stage's *applied* changes rather than summarising them ("refactor applied several fixes" leaves hunks belonging to no stage, and the retro has to re-derive attribution from the diff, and name each *returned* finding with its disposition rather than counting them — "security-review returned 2, applied none" leaves the retro unable to tell whether a finding was answered, deferred or dropped, and unlike an applied fix it appears in no diff to recover it from) — then spawn `idsd-retro` as a **fresh** subagent (per **Spawn the skill**), handing it the run-log plus the diff and any skill/doc/prompt/script the run touched. Derive the touched-files list from `git diff --stat` against the base, not from memory — the diff is authoritative, so never tell the retro a file is "unchanged" when it shows in the diff (if it was reviewed in an earlier round this session, say *that*, don't hide it). It owns the adversarial method and lenses; it returns routed, evidence-backed findings.
   - **Split retro's findings by kind — only a defect in *this change* gates.** A finding that's a defect the run introduced (a bug or risk, or a fix to fold back in) → record as a gating **Decide**, like any other stage. A finding that's an improvement *for next time* (a better rule, a tooling tweak, a standard worth adding) → route it to a home that gets **consumed**, never a file nothing reads: a skill/standard/tooling improvement → propose it to the human in the gate message (the skills are files the human owns — approved means applied now, in their repo's working tree; deferred means a memory entry in the user-global `CLAUDE.md` Memory section — which loads at the *start* of every session, so an entry written mid-session is inert for the rest of it: carry a mid-session deferral into the spawn prompt of every stage that runs afterwards, or it will be breached by the same run that wrote it, as observed twice in one session); a project follow-up → the ICE's `## Follow-ups`; a durable standard → a constitution proposal. Leave the report just **one non-gating line under Watch**, e.g. `- 5 retro follow-ups filed → <home>`. A run-improvement is a follow-up, never a gating `- [ ]`. Record nothing only when the run surfaced no improvement (a course-corrected run never does).

**Full mode verifies the gates are real before stamping.** Read what CI actually invokes (the workflow definition) and confirm the repo's baseline gates — build, lint, tests — run and read the changed code: a gate that can't run, is never invoked, or has zero overlap with the diff becomes a **Decide** item, never an assumed green (one package's lint gate sat dead for over a year because every review assumed CI ran it). Under `idsd-ship`, `idsd-build`'s Phase 2 already resolved the gates — don't redo it; this check covers the standalone path.

When all stages complete, stamp the fingerprint: `report.sh stamp "<stage entries>"` — it computes `git write-tree` (via a throwaway index; it never touches the human's staging area) and writes `reviewed-tree` plus `reviewed-stages`, every pipeline stage accounted for, comma-separated: bare when it ran (`code-review,…,refactor`), qualified when it didn't — `:skipped(fast)` for a turnaround skip, `:skipped(no-surface)` / `:skipped(no-prose)` for an unmet condition, `:skipped(off)` for a pipeline flag — and `refactor:partial(fast|cap)` when its loop ended non-compliant (fast's single iteration, or full's cap). Record honestly: the merge gate reads this stamp, any `(fast)` entry marks the pass as not-full, and a stage that ran is never stamped skipped — or vice versa. A corollary, by design: a fast pass whose every stage ran to completion stamps with no `(fast)` entries and passes the merge gate — the gate measures the work done, not the label invoked.

**Report post-processing.** After stamping, when `config.yaml` → `post` → `report-tighten` is true and the report has items, apply the `tighten` role's lens inline over `.idsd/ship-report.md` before presenting — no subagent; the report is small by contract. Lossless applies in full: every item and its stakes survive, and it never drops or softens a `- [ ]`. The `humanize` role does not apply — the report's audience is the human mid-run, so house style holds. (The report is check-ignored, so tightening it never invalidates the stamp.)

## Report

`ship-report.md` **always** lives at `.idsd/ship-report.md` and **persists across runs** — the working digest, never committed (git history — and under idsd, the ICE — is the durable record). `scripts/report.sh` (this skill's dir) owns the path and every deterministic operation — init, invalidate, stamp, carry, check-ignore, plus the ones serving `idsd-ship`'s lifecycle (repo-mode, gate, state, promote, discard — mechanics documented there) — never done by hand.

**Two repo modes — committed vs throwaway — decided by whether `.idsd/` is tracked in git** (`report.sh repo-mode` prints which). This load-bearing distinction drives how the report stays out of git and whether `.idsd/` is durable:
- **Committed** — the repo has *committed* `.idsd/` content, so it durably uses idsd. The report is ignored via a **shared, tracked `.gitignore` entry** (`.idsd/ship-report.md`), and `.idsd/` changes are part of the durable record.
- **Throwaway** — no `.idsd/`, or an untracked one a single-shot run created. The **whole `.idsd/`** (intents *and* report) is excluded locally via `.git/info/exclude`, so it leaves **zero traces** across any number of runs and **never touches `.gitignore`**. `.idsd/` is never committed unless the human promotes it (`idsd-ship promote`).

**Never commit the report or a `.gitignore` diff for it.** `report.sh check-ignore` (run before any stage) applies the mode's mechanism so the fingerprinting `git add -A` (stamp/gate) can never stage the report — committed mode asserts the tracked entry and WARNs if missing (add it), throwaway mode ensures the local `.idsd/` exclusion. Either way the report is local scratch, never staged, never committed.

### Structure

```markdown
---
intent: <NNN-slug or "review: <description>">
reviewed-tree: <git tree hash at time the pass completed>
reviewed-stages: <every pipeline stage, bare (ran) or qualified (skipped/partial, with reason)>
---

# Decide

<optional: 2–3 sentences of context several items share — stated once here, never per item>

- [ ] **<the decision, one line>** — recommend: <one clause>.
  <the case: what it is, why it matters, the evidence — indented under the bullet>

# Watch
- <a monitor-only item; no action now>
```

`idsd-ship done` checks `reviewed-tree` against the current tree and `reviewed-stages` for turnaround trims — unreviewed changes and fast-only review both block. The report is **only the residue that needs the human — not a record of the run**. At most two groups, each present only when it has items — **Decide** (`- [ ]` actions) and **Watch** (monitor-only) — with no per-stage sections and no summary. Order Decide by decision kind, so attention lands where thought is needed: **forks** (a genuine choice still open) first, **ratifications** (bless or reverse work already applied) second, **pending evidence** (can't settle until a named signal arrives, e.g. the next hardware run) last. On re-qualify **every unresolved `- [ ]` carries forward verbatim** — dropped only with positive evidence it's resolved (fixed in the tree, or the human acted on it), never because this pass didn't re-examine its area; new findings append as fresh `- [ ]`. Watch bullets are re-evaluated each pass — kept while relevant, dropped when moot.

### What goes in (and what never does)

The report holds the *non-blocking* attention set — decisions to ratify, deferrals, gated/declined fixes, monitor-only watches — never a blocking question (asked live, per Interactive first).

One exception, earned the hard way: **a question you asked live and the human did not answer becomes a `Decide` item when the pass closes.** Chat scrolls; the report does not. A stray untracked file was raised in passing across three rounds, never answered, and stayed invisible to the report while actively degrading the duplicate-text evidence every round — that is the failure this prevents.

**Every item must stand on its own — within the report.** Someone reading only the report — who never saw the run or this chat — must understand *what it is* and *why it matters*, in plain language, and be able to act. When several items lean on the same background, state it once in a short preamble under `# Decide` and let the items build on it: self-containment holds at report level, never by repeating context per item. Cut run-narration and jargon: no "what we tried", no dependency lists, no command strings, no private tags — state the thing in plain words, adding the exact identifier in parentheses when it's the fastest anchor for the reader. But never cut the stakes — a one-liner that only makes sense if you were there fails the bar as surely as bloat does, so spend the sentence or two it takes. If an item can't be self-contained without pasting run detail, that detail belongs in a durable home (backlog, ICE, commit) and the report links to it.

A **Decide** item opens with the decision in **one bold line** ending `— recommend: <your resolution>` (earned by legwork, per Interactive first — never a bare choice); the case — what it is, why it matters, the evidence — follows indented under the bullet. The reader triages the bold lines first and reads a case only where they don't immediately agree, so the ask is never buried mid-paragraph. Tag an item's origin stage in plain words only when that aids the human. A **Watch** item is monitor-only, no checkbox — a thing to keep an eye on, or a one-line pointer to follow-ups routed out of the report. Watch never gates a merge.

**The test: if the human takes no action, it is not in the report.** A resolved or applied fix, a passed / clean / not-applicable stage, "here's what changed", and any verification narration are all **omitted** — they live in the diff, the commit, and the fact the pipeline ran. The report shrinks to nothing when nothing needs the human — that's the success case, not an omission. The one exception is a fix the human might want to *reverse*: record that as a Decide item (ratify or revert), not as an FYI.

## After the pass

**The report is the single source of substance; the chat message is short.** Everything the human must read, decide, or act on lives in `.idsd/ship-report.md`, self-contained — so they read *one* place. The chat message after a pass contains only:
- **one status line** — the mode of this pass, the repo mode (throwaway/committed), and the item count broken down by decision kind (e.g. "full pass: 5 to decide — 2 forks, 2 ratifications, 1 pending evidence — and 1 to watch"), or "report is empty — nothing needs you";
- **the next-step actions** (below);
- **at most one live blocking question** (per *Interactive first*).

It must **not** contain: per-stage results or verdicts, a retro narrative, a restatement or preview of the report's items, or "here's what changed" — if something is worth the human's attention, it goes **in the report**, not into a chat paragraph. When the pass follows an `idsd-ship` build, the one exception is `idsd-build`'s checkpoint evidence (gate + scenario + observed outcomes) — surface that alongside the pointer.

**Next-step actions** by context:
- **Under `idsd-ship` (an intent):** review the diff and the report; changes → `/idsd-ship qualify` re-runs fast; ready → `/idsd-ship done` (its gate demands a fresh full pass — run `/idsd-ship qualify full` first if this pass was fast or the tree moved).
- **Standalone working tree:** review the diff and the report; changes → `/idsd-qualify` again; before merging or opening a PR from this change → `/idsd-qualify full`.
- **Throwaway repo mode:** add **one line**: `.idsd/` is local scratch this run (excluded, nothing committed, zero traces) — `/idsd-ship promote` to keep it.

## PR target

`idsd-qualify pr <ref>` — review a GitHub PR with the same pipeline and return a **drafted review**, not applied changes. `<ref>` is a PR number, URL, or head branch (`gh` must be authenticated). Defaults to **full** (a PR review is a pre-merge verdict); pass `fast` explicitly to trade refactor's completeness loop for turnaround (the parallel round is the same in both modes). Retro never runs (there's no run of ours to retrospect), and the report machinery isn't used — the residue channel *is* the review; accumulate the draft in a scratch file, not in `.idsd/`.

- **Checkout.** Resolve the PR (`gh pr view <ref> --json number,url,title,baseRefName,headRefName`), fetch its head (`git fetch origin pull/<N>/head`) and check it out in a disposable worktree (`git worktree add <scratch>/pr-<N> FETCH_HEAD`). The review scope is the PR diff — fetch the base branch and diff `origin/<base>...HEAD`. Remove the worktree when done.
- **Run the stages there, unchanged — with one exception.** Stages apply their fixes inside the worktree exactly as on a working tree — it's scratch whose diff becomes the review; nothing in it is ever committed or pushed. The exception: skip tighten's humanize handoff entirely — outward files and the author's code comments alike keep the author's voice, so a lossless cut may become a suggestion but a voice rewrite never does; humanize applies only to the review we draft (below).
- **Map the outcome to the review.** A fix a stage applied → a ` ```suggestion ` comment on the lines it changes, when those lines are in the PR diff (GitHub anchors comments only to diff lines); otherwise describe the change in the summary body. A finding returned unapplied → a line comment stating the problem, why it matters, and the fix (severity + exploit scenario for security findings). Cross-cutting residue — what Decide/Watch would hold — goes in the summary body, same self-containment bar as the report.
- **The review is outward text.** Draft the summary and every comment under `~/.kk-flavor/standards/human-writing.md`, and apply the `humanize` role's lens inline over the complete draft before showing it — it's your own writing, so no spawn.
- **A question only the PR author can answer is a review comment, not a live block** — post it on the relevant line as a question. Setup ambiguities (wrong base, gates can't run) are still asked live.
- **Post only on approval.** Show the human the complete draft — summary plus every comment — and post only when they approve, as one review: `gh api repos/{owner}/{repo}/pulls/<N>/reviews` with `event=COMMENT` and the comments array (path, line/start_line, side, body). Never approve or request changes unless the human explicitly says so; never push to the PR branch.

## Rules

- Adds only sequencing and the digest; the stage skills own the actual work.
- **A change to a pipeline script lands its call site in the same edit.** A subcommand nothing invokes is not a half-finished feature, it is an invisible one: `stage-returned` sat in `report.sh` for hours with no line here telling any orchestrator to call it, and the gap surfaced only when an unrelated refusal sent someone reading the script. The same goes the other way — a rule stated here that no script enforces is prose, and prose is what the mechanism was added to replace.
- **Never commits or pushes.** Fixes stay in the tree for the human; committing is the caller's or the human's act — a mid-qualify commit publishes a state the review hasn't finished with. Any verification that reads a ref (e2e, hardware) runs against the stamped `reviewed-tree`, not the remote.
- **A live verification is void the moment a stage changes the path it exercised**, so sequence it after the pass rather than before. Run one early and the stages then rewrite that path — as they will, since it is the path the change is about — and what you have is an expensive result describing a tree that no longer exists. Asked for one mid-pass, run it, but re-run it at the end and report only the second result; a stage that changed nothing it touched is the only case where the first still stands, and that is a claim to check against the diff, not to assume.
- A stage that hard-fails (red gate, broken build) stops the pipeline — never relax a sub-skill's gate to keep moving; a blocking decision is asked live, not recorded to dodge it.
- **While a stage is live, the tree it was told to read must not move under it.** No rebase, cherry-pick, reset, branch switch or base change in the target repo until the in-flight stage returns. A subagent keeps reading files for the whole of its run, so a rewrite mid-stage feeds it a mixture of two trees and its verdicts then describe neither. Expect to be asked mid-pass anyway — a squash-merged parent blocks every PR stacked above it, so the human will want the stack fixed now. Either finish the stage first, or abandon it, do the maintenance, then `report.sh invalidate` and spawn it fresh against the new HEAD. A separate worktree is the only way to overlap the two safely.
- Keep chat lean — but *lean* is not *cryptic*: the "stand on its own" bar applies to every human-facing message (the next-step message, any live explanation), not just report lines. And a pointer must point at real substance: don't claim something is "filed"/"noted"/"routed" unless it lives in a named durable home that actually contains it — a pointer to nothing is worse than saying it plainly.
