# Memory

Add new memory entries to this section. Do **not** create or write to per-project memory dirs (`~/.claude/projects/*/memory/`) — keep all memory here.

This is a staging area. Once enough memory accumulates, the user folds entries into the proper sections of this document. Do not reorganize on your own. Entries here are authoritative — apply them as if they were in a structured section.

- **A quality stage's own non-trivial fix is unreviewed code.** When a review stage applies a behaviour-changing fix of any size, nothing in the pipeline then reviews it for correctness — the stage that wrote it is not a second opinion. So a stage applying such a fix must land a test per branch it introduces. Observed: a code-review stage authored ~52 lines of an abort seam, and a defect in it (an already-aborted path removing an event listener it had never added) survived until a later refactor pass happened to look.

- **A change that starts depending on an in-repo sibling puts that sibling's public surface in review scope.** Scoping review to "what git says changed" misses the file the change newly leans on, even when that file plainly violates a documented rule. Observed: `runPeriodically` began delegating to `callWithTimeout`, whose 3-positional-param signature already broke the named-params rule; no stage raised it and the user did, twice mid-flight, growing the change set from 2 files to 5.

- **An untracked file at a repo root can break the dev launcher, so rule the working tree out before blaming the install.** `tsconfig-paths` resolves plain package names against `baseUrl` as well as `node_modules`, and with `resolveJsonModule` a JSON file counts — so a stray `<package-name>.json` at the root shadows that package for every dependency requiring it. Observed in player-testautomation: a 445 KB `debug.json` jest dump made every `npm run start:ts` die on `debug_1.default is not a function` from inside `engine.io-client`, while the compiled `npm start` was fine. The error named neither the file nor our code, so it read as a broken `node_modules`. Settles in one step: run the same require under plain `node`, then `ts-node`, then `ts-node -r tsconfig-paths/register` — whichever first fails names the culprit layer.

- **Considered and not built: a `positional-params.sh` check for `idsd-qualify`.** A grep over a diff's added exported signatures for 3+ positional params, riding refactor's evidence slot like `dup-literals.sh` does. Declined as marginal on one observed miss — revisit only if positional-param signatures recur across runs.

- **A retro finding aimed at the tooling is written the moment it is ratified, or it does not survive.** Chat is not a durable home and neither is a throwaway `.idsd/`: the moment Kirill approves a skill or standard change, edit the file in `~/Documents/WP/configs` then and there; if he defers, the entry goes here instead. Observed across two consecutive passes on one branch: eight findings were "proposed in chat" and filed nowhere, and one of the five pipeline changes among them recurred in the very next pass — a stage acted on ground a follow-up called deferred, which is the same class as the report items the earlier finding said to retract. The recurrence cost a second retro to rediscover.

- **Awaiting a ruling, nine review-tooling findings from the abort-race pass (5 August) — apply on approval, don't re-derive.** Recommended six first. **(a) `stamp` takes its stage list on faith:** it validates the entry *shape* only, so it accepted `refactor,retro` while neither had run, and only iterates markers that exist — an unmarked stage is indistinguishable from a compliant one. Refuse a bare entry with no return marker; only `:skipped(reason)` may lack one. **(b) The freshness check is one shared `-newer "$report"` mtime,** so it is neither per-stage (a concurrent round's two markers are both cleared by whichever stage's items you record first) nor order-independent (marking *after* recording blocks work you did do). Snapshot the report's checksum per marker instead; that also deletes the ordering caveat rather than trusting prose. **(c) A stage with genuinely nothing to record cannot clear its marker:** `stamp` says "or note there were none", but the only way to clear it is a report edit and the format bans per-stage lines. Add `report.sh no-items <stage>` or accept `<stage>:no-items`. **(d) The capability landed half-wired** — `stage-returned` existed in the script for hours with nothing instructing its use; a pipeline script's call site lands in the same edit. **(e) A live/hardware verification is void once a stage changes the path it exercised** — an e2e run before the pass described a tree that no longer existed; sequence it after, or re-run against the stamped `reviewed-tree`. **(f) The 3+-positional-params rule needs the exceptions actually used:** a pre-existing signature the change isn't otherwise touching, and a published package's public surface — declined three times in one session against a rule that reads unconditional, see [[considered-and-not-built-positional-params-check]]. Then the four to defer: comment density measured only before the last stage, so earlier spawns read the inflated file; a decision table over a closed enum should be enumerated in a table-driven test *before* the pass (three stages each found one missing cell of one table); the orchestrator's own fixes ship untested unless a later stage happens to ask; and no stated policy for adding a case to a pre-existing mock-based test file.

- **Declined on 5 August, four `idsd-qualify` improvements — don't re-propose without new evidence.** (1) Query SonarCloud once per pass and feed issues/hotspots to code-review and security-review through the tool-output slot, reusing the `sonar-api` skill; today the orchestrator fetches it by hand and security-review returns "no Sonar data". (2) Retro findings carry a *state* rather than a count, so a Watch line can't claim twenty-five unfiled items when most are filed. (3) A comment quoting a measured value names the measurement, and code-review must re-measure before contradicting one — code-review spent a live probe disproving itself against a number two earlier rounds had already measured (`maxRetryAfter` → `Infinity`). (4) Hold a fix the *orchestrator* applies outside any stage to the same licence a stage's fix gets; a one-issue Sonar instruction became five conversions.

- **A repo `CLAUDE.md` for player-testautomation was declined on 5 August after four rounds proposed it.** Until that changes, these facts get hand-carried into each spawn prompt: a stray `<package-name>.json` at the repo root shadows that package under `tsconfig-paths`; the stacked TA-2488/TA-2866 branches pin incompatible `player-testing-utilities` versions so switching between them needs `npm ci`; and `Scheduler › onJobFinished event contains duration` is a pre-existing timing flake. See [[an-untracked-file-at-a-repo-root-can-break-the-dev-launcher]].

- **Exit status is not evidence on Docker Swarm or an appliance-style admin API — verify the effect, and check identity rather than liveness.** Four commands in one run reported success and did nothing. `docker service update --force` restarted tasks on the digest the service was created with while the registry held a newer one, so a rebuilt site kept serving stale bytes; `--image <ref>` alone was then a no-op because the spec already held that exact ref, so picking up a re-pushed tag needs **both** flags. `x-ui restart` returns success without restarting the process inside a container (a `service update --force` is required). `docker exec` without `-i` silently ran a piped script as a no-op. Throughout, an HTTPS 200-with-valid-cert check kept passing — it proves the service is alive, never that the deployed artifact is the one you built. Compare served bytes against the source file, or the running digest against the registry.

- **A secret a run mints lives in exactly one place, and "remove all artifacts" includes the agent's own scratchpad.** A retro found the live panel password in three scratchpad files and the reality private key in a fourth, while the report was simultaneously telling the human those secrets existed "only on the server, with no second copy" — the cleanup pass had swept the server and its git checkout but never the scratch dir where the secrets actually were. Before asserting where a secret lives, grep the run's own scratchpad for it; better, never write it to disk.

- **Re-form the commit after the quality pass: a change set staged mid-run goes stale the moment a later stage edits files.** Staging happened before the pass; code-review, tighten, refactor and humanize then edited six of those files, leaving `MM`/`AM` in `git status`. A bare `git commit` would have shipped the pre-pass tree — including a factual error the pipeline had already corrected. Run `git add -A` after the last stage, and never re-present a commit command formed earlier in the run.

- **Never learn an undocumented admin API's shape by sending it a write payload on a live system.** Probing `POST /panel/api/xray/update` with `xraySetting={}` returned `success: true` and cut the stored xray config down to a single key, dropping inbounds, outbounds, api, log, metrics, policy and stats. Recovery worked only because a copy had been fetched moments earlier by luck rather than design. The method that should have come first, and did work: read the routes out of the binary's strings, then use the read endpoint. If a write probe is unavoidable, snapshot deliberately and keep the snapshot until the change is verified.

- **Read the repo's own runbook for an operation before improvising a path for it.** Deploying `reverse-proxy` from `/tmp` made its relative bind mounts resolve to nothing; the task was rejected and every site was down for minutes — while the README already prescribed the absolute repo path. Relative paths in a compose file resolve against the directory that file sits in, so "any copy of the file" is not equivalent.

- **A finding that proposes building a subsystem states its standing cost inside the finding.** A nightly backup system was designed, built and verified on "address all your findings properly", then removed in full one message later when the human named the constraint — on a box where the same run had already reclaimed 10.8 GB because disk was tight. Naming the footprint (disk, RAM, schedule) at proposal time puts the decision before the build instead of after it.
